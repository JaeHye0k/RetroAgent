01한눈에 보기

외부 시스템은 셋, 내 Mac 에서 도는 프로세스는 하나다.

설계의 핵심 한 줄

LLM 은 텍스트를 JSON 으로 바꾸는 일만 한다. 노션 API 호출, 페이지 탐색, 블록 삽입 위치 계산, 날짜 판단, 큐 관리는 전부 일반 코드가 처리한다.

이렇게 나눈 이유는 두 가지다. 실패할 수 있는 지점이 한 군데로 좁혀지고(그래서 그 한 군데에만 폴백을 두면 된다), 나머지 전부를 단위 테스트로 검증할 수 있다.

02세 시스템의 역할 분담

각 시스템이 무엇을 하고, 무엇을 하지 않는지가 구조를 결정했다.

Telegram

입력과 승인 창구.

  • 조각글을 아무 때나 받는다
  • 미확인 메시지를 24시간 보관 — 맥이 자는 동안 온 것도 깨어나면 들어온다
  • 인라인 버튼으로 승인·취소를 받는다
  • chat_id 화이트리스트가 유일한 인증
하지 않는 것 — 조각글을 저장하지 않는다. 24시간이 지나면 사라지므로 받는 즉시 로컬 큐에 적는다.

Claude Code

줄글을 구조로 바꾸는 단 하나의 일.

  • claude -p 를 자식 프로세스로 부른다
  • --json-schema 로 출력 형태를 강제한다
  • --tools '' — 도구를 전부 끈다
  • --safe-mode — CLAUDE.md · 훅 · MCP · 플러그인 차단
하지 않는 것 — 노션을 만지지 않는다. API 키도 모르고, 어느 페이지에 쓰는지도 모른다. 받은 텍스트를 JSON 으로 돌려주고 끝난다.

Notion

최종 저장소.

  • 회고 DB 를 날짜 + 주기=일간 으로 조회
  • 페이지가 없으면 템플릿 뼈대와 함께 만든다
  • 섹션 헤딩 아래 정확한 위치에 블록을 끼워넣는다
  • Internal Integration 토큰으로 REST 직접 호출
하지 않는 것 — 상태를 갖지 않는다. 무엇이 아직 정리되지 않았는지는 노션이 아니라 로컬 queue.jsonl 이 안다.
왜 MCP 를 쓰지 않았나. Claude Code 에 이미 연결된 Notion MCP 는 OAuth 방식이라 백그라운드 프로세스가 재사용할 토큰이 없다. 세션이 만료되면 새벽에 조용히 실패한다. 그래서 노션은 Integration 토큰으로 직접 호출하고, Claude 에게는 노션 접근 권한을 아예 주지 않았다.

미리보기는 04 단계의 JSON 을 텔레그램 텍스트로 그린 것이다(render.js). 즉 승인 화면과 노션에 들어갈 내용은 같은 데이터에서 나온다 — 보이는 것과 저장되는 것이 어긋날 수 없다.

왜 LLM 에게 노션 블록 JSON 을 직접 만들게 하지 않았나. 블록 스키마는 중첩이 깊고 필드 이름이 까다롭다(annotations.color 는 글자색, quote.color 는 블록색). LLM 이 여기서 한 글자 틀리면 저장이 실패한다. 대신 04 의 단순한 형태만 맡기고, 05 변환은 테스트가 붙은 순수 함수로 두었다.

04하루 동작 타임라인

평소에는 조용히 받아두기만 하고, 정해진 시각에 한 번 말을 건다.

이 사이에 도는 두 개의 루프

루프주기하는 일
폴링 50초 long-poll 텔레그램에 매달려 있다가 메시지가 오면 즉시 처리. 실패하면 1초 → 최대 60초 백오프. 요청은 65초에 강제로 끊는다.
스케줄러 30초 간격 “정리할 때가 된 날짜가 있나?”만 확인. 대부분의 틱은 아무것도 하지 않고 끝난다.

05회고 날짜는 어떻게 정해지는가

여기가 이 프로젝트에서 가장 미묘한 부분이다. 날짜를 “지금”이 아니라 조각이 쓰인 시각에서 뽑는다.

며칠 밀렸을 때

큐를 ts 로 날짜별로 묶고, 한 회차에 한 날짜만 다룬다. 가장 오래된 날짜부터 미리보기가 오고, 승인하면 다음 날짜가 이어서 온다.

상황동작
월·화·수 조각이 섞여 있고 목요일 아침월 → (승인) → 화 → (승인) → 수 순서로 각각 자기 날짜 페이지에 저장
어제 몫과 오늘 몫이 섞여 있고 오늘 오전어제 몫만 발송. 오늘 몫은 오늘 23:00 을 기다린다
/now 를 눌렀다임계 시각과 처리 이력을 무시하고 가장 오래된 날짜부터 정리
미리보기를 취소했다스케줄러는 그 날짜를 다시 들이밀지 않는다. /now 로는 다시 꺼낼 수 있다
ts 가 깨진 조각버리지 않고 오늘 몫으로 넣는다

06승인 상태 머신

정리 결과는 pending.json 에 담긴 채 사람의 판단을 기다린다.

재시도가 중복을 만들지 않는 이유. 두 섹션을 순서대로 삽입하는데, 첫 섹션은 성공하고 두 번째에서 실패할 수 있다. 그대로 재시도하면 첫 섹션이 두 번 들어간다. 그래서 섹션 단위로 progress 를 pending.json 에 기록하고, 재시도 시 이미 끝난 섹션은 건너뛴다.

07노션 페이지의 어디에 넣는가

페이지 끝에 붙이면 안 된다. 오늘 한 일 은 오늘 한 일 섹션 안으로 들어가야 한다.

노션 API 는 “이 블록 뒤에 넣어라”(after)만 받는다. 그래서 페이지의 최상위 블록을 읽어 섹션의 마지막 블록을 직접 찾아야 한다.

heading_2오늘 한 일
quote오늘 있었던 일·활동을 사실 위주로…
paragraph (bold)장바구니 개선
bulleted_list_item담기 버튼 버그 수정← 기준점 (after)
paragraph (bold)결제 단계 개선새로 삽입
bulleted_list_item로그를 심으려다 배포까지 못 함새로 삽입
divider———여기서 탐색 중단
heading_2한 줄 배움 / 감정
quote오늘 배운 것, 느낀 감정을 한 줄로…

탐색 규칙은 세 줄이다.

  1. 텍스트가 섹션 제목과 같은 heading_2 를 찾는다
  2. 거기서부터 아래로 내려가다 divider 또는 다음 heading_2 를 만나면 멈춘다
  3. 멈추기 직전의 블록이 기준점 — 그 뒤에 삽입한다

섹션이 비어 있으면 기준점은 가이드 quote 가 된다. 섹션 헤딩 자체가 없으면 헤딩과 가이드를 함께 만들어 페이지 끝에 붙인다.

두 섹션을 삽입할 때 매번 페이지 블록을 다시 읽는다. 첫 삽입이 두 번째 기준점의 위치를 흔들 수 있어서다. API 호출 한 번을 아끼는 것보다 어긋나지 않는 게 중요하다.

09실패하면 어떻게 되는가

전 구간을 지배하는 하나의 규칙 — 조각글은 유실되지 않는다.

실패 지점대응조각글은
텔레그램 연결 끊김 1초 → 최대 60초 백오프 재시도 텔레그램이 24시간 보관 → 복구되면 들어온다
잠자기 후 소켓이 죽어 매달림 AbortSignal.timeout() 으로 끊고 백오프 경로로 진입 안전
claude -p 출력이 스키마와 다름 형식을 지적해 1회 재시도 큐에 그대로
재시도도 실패 / claude 미설치 / 사용량 초과 폴백 draft — 원문 전부를 미분류 로. 미리보기에 경고 표시 원문 그대로 노션에 들어간다
노션 429 / 5xx / 타임아웃 Retry-After 존중, 최대 3회 재시도 큐에 그대로
노션 저장 최종 실패 큐를 비우지 않고 재시도 버튼 제시 큐에 그대로 — 다시 시도 가능
첫 섹션만 저장되고 실패 progress 에 기록 → 재시도 시 그 섹션은 건너뛴다 중복 없이 이어서 저장
정리 결과가 마음에 안 든다 🔄 다시 정리 · 또는 저장 후 /undo /undo 시 큐로 복원
맥이 24시간 넘게 꺼져 있었다 구조적 한계 — 텔레그램 보관 기간을 넘긴다 유실. 장기 부재가 예상되면 클라우드 전환이 답

불변 조건 셋

1. 노션 저장이 성공하기 전까지 큐에서 조각을 빼지 않는다.

2. 큐에서 뺄 때도 삭제가 아니라 아카이브로 옮긴다.

3. 어느 실패 경로로 가도 원문은 어딘가에 남아 있다 — 큐, 아카이브, 또는 미분류 로 들어간 노션 페이지.
